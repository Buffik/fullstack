# fullstack

level up to octopus has begun

План перехода с middle+ frontend (React, TypeScript) на бэкенд больших проектов. Курс по BFF идёт первым и на Express. Дальше закрываются пробелы, без которых Nest на большом проекте остаётся набором декораторов: Docker, реляционная база, ORM, кэш, брокер, поиск.

Ориентир после курса BFF: 18–20 недель при 6–8 часах в неделю. Цель каждого этапа — рабочий уровень: сделать фичу, прочитать чужой код и объяснить решение на ревью. Администрирование кластеров, Kubernetes и тюнинг баз в план не входят.

## Что уже есть

- TypeScript, асинхронный код, контракты API, состояния ошибок.
- React: границы компонентов и композиция. В Nest похожая идея у модулей — у каждого модуля свой публичный контракт, внутренности наружу не торчат.
- Клиентский кэш (если пользуетесь React Query или аналогом): ключ, инвалидация, устаревшие данные. Серверный кэш опирается на те же вопросы.
- После курса BFF: HTTP-сервер, middleware, агрегация ответов, MongoDB.

## Пробелы и зачем они в этом порядке

| Тема | Зачем она до следующей |
|---|---|
| Docker | Postgres, Redis, брокер и Elasticsearch поднимаются одной командой, без ручной установки на машину |
| Реляционная БД и SQL | ORM показывает запросы, которые вы уже понимаете. Иначе Prisma скрывает и связи, и стоимость запроса |
| Nest | Каркас сервера. База к этому моменту уже есть, и в неё есть куда положить домен |
| ORM | Схема, миграции и транзакции внутри Nest, поверх уже написанного SQL |
| Кэш | Имеет смысл только когда есть источник данных, который кэшируют |
| Брокер | Асинхронная граница появляется после того, как синхронный сценарий уже работает |
| Elasticsearch | Отдельная модель чтения для поиска. Появляется, когда данные уже живут в Postgres, а SQL для поиска становится тесным |

Сквозной учебный сервис — каталог и заказы. Его же потом можно вызвать из BFF. На каждом этапе к сервису добавляется один инфраструктурный кусок, а предыдущие остаются работать.

Как учимся: короткая теория, задание, вы пишете код сами, присылаете diff на разбор. Файлы проекта меняются только по вашей явной просьбе. Продолжать лучше в том же чате. В новом диалоге напишите номер этапа и что уже сделано.

## 0. Курс BFF — Express и MongoDB

Срок задаёт курс. Nest до его конца не начинать.

Закрыть своими руками, даже если курс даёт это готовым:

- Роут, middleware, обработка ошибок, таймаут внешнего вызова.
- Агрегация нескольких ответов в один контракт для клиента.
- Модель документа MongoDB: вложенный объект, ссылка на другой документ, когда какой вариант уместен.
- Индекс в MongoDB на поле, по которому реально ищете.

Итог: тонкий BFF, который ходит в чужие API и отдаёт один ответ фронту. Этот сервис остаётся на Express. Доменный API дальше пишется отдельно.

## 1. Docker для разработки

Около 1 недели. Ровно столько, сколько нужно, чтобы поднимать зависимости локально.

- Образ, контейнер, порт, volume, переменные окружения.
- `docker compose up` для одного Postgres.
- Логи контейнера, заход внутрь, пересоздание без потери данных и с потерей данных — оба сценария.
- Файл compose живёт в репозитории учебного сервиса и пополняется на следующих этапах.

Итог: Postgres поднимается одной командой, данные переживают перезапуск контейнера.

Сознательно позже: свои Dockerfile для продакшена, multi-stage сборка, Kubernetes.

## 2. Реляционные базы и SQL

Около 3 недель. Самый важный пробел относительно MongoDB из курса BFF.

Пройти на PostgreSQL, запросы писать руками через `psql` или клиент базы. ORM на этом этапе нет.

- Таблица, строка, первичный ключ, внешний ключ, `NOT NULL`, `UNIQUE`.
- Связи один-ко-многим и многие-ко-многим. Сравнить с тем, как то же самое лежало бы документом в MongoDB.
- `JOIN`, `GROUP BY`, агрегаты.
- Индекс: когда ускоряет чтение и чем платит на записи. Посмотреть план через `EXPLAIN`.
- Транзакция и изоляция на одном сценарии: списание остатка и создание заказа либо проходят вместе, либо откатываются вместе.
- Нормализация до практического уровня: заказ хранит снимок цены на момент покупки, а не только ссылку на товар.

Учебная схема:

- `users`
- `products`
- `orders`
- `order_items`

Итог: вы напишите запросы «заказ со строками и товарами», «остаток не уходит ниже нуля» и объясните, зачем здесь транзакция.

## 3. Каркас Nest.js

Около 2 недель. База пока снаружи, Nest учится на фоне Express из BFF.

- CLI, `main.ts`, корневой модуль.
- Модуль, контроллер, провайдер, внедрение зависимостей.
- Соответствие Express: контроллер — роут, провайдер — сервис с логикой, модуль — граница фичи.
- Один ресурс `products`: список и создание. Логика живёт в сервисе, контроллер только принимает и отдаёт.

Итог: вы можете провести запрос от HTTP до метода сервиса и сказать, кто кого создаёт.

## 4. ORM

Около 2 недель. Один инструмент — Prisma. TypeORM в документации Nest тоже встречают; принцип тот же, второй ORM параллельно не учить.

- Схема Prisma на таблицах из этапа 2, миграции, генерация клиента.
- Репозиторий прячет Prisma. Сервис не собирает запросы сам.
- Транзакция из этапа 2, переписанная через Prisma.
- Посмотреть SQL, который Prisma отправляет в Postgres. Узнать свой `JOIN` в этом SQL.

Итог: схема меняется миграцией, сценарий заказа атомарен, сервис не импортирует клиент Prisma напрямую.

## 5. Форма серверного приложения

Около 2 недель. То, что на большом проекте ожидают сразу.

- DTO и `ValidationPipe`.
- Guard на проверку прав, exception filter с единым JSON ошибок.
- Interceptor для времени запроса. Middleware оставить для сырого HTTP.
- JWT: выдать токен, пустить в защищённый метод, отказать чужому.
- Swagger из тех же DTO.
- Юнит-тест сервиса с подменой репозитория.
- Один e2e-сценарий через HTTP. Базу в этом тесте поднимать, внешние вызовы подменять.
- Конфиг через переменные окружения, health check.

Итог: невалидное тело даёт 400, чужой доступ — 403, доменная ошибка — предсказуемый JSON. Чужой разработчик поднимает сервис по README этого сервиса.

## 6. Кэширование

Около 1,5 недели. Redis добавляется в тот же compose.

- Модель cache-aside: промах — читаем Postgres и кладём в Redis, попадание — отдаём Redis.
- TTL на карточке товара.
- Инвалидация при обновлении товара. Устаревшая цена в кэше — главный учебный случай.
- Что кэшировать уместно (карточка товара, справочник) и какой запрос оставлять без кэша (создание заказа, проверка остатка).

Итог: повторное чтение карточки не ходит в Postgres, обновление товара убирает старое значение из Redis.

## 7. Брокер сообщений

Около 2–3 недель. Сначала RabbitMQ как учебная модель. Kafka — отдельным коротким блоком в конце этапа: на больших проектах её встречают чаще, но понятия проще закрепить на RabbitMQ.

RabbitMQ, в том же compose:

- Producer и consumer в процессе Nest.
- Очередь, подтверждение обработки, повтор при падении потребителя.
- Сценарий: заказ создан синхронно в Postgres, письмо и пересчёт статистики уходят сообщением.
- Идемпотентность: одно и то же сообщение дважды не создаёт второй заказ и не списывает остаток дважды.

Затем Kafka на уровне понятий и одного упражнения:

- Лог сообщений, потребитель, группа потребителей, смещение.
- Тот же факт «заказ создан» прочитать отдельным потребителем.

Итог: HTTP-запрос создания заказа не ждёт рассылку. Повторная доставка не портит данные. Вы отличаете очередь задач от журнала событий.

## 8. Поиск — Elasticsearch

Около 2 недель. Elasticsearch добавляется в compose. Источник данных по-прежнему Postgres.

- Зачем отдельный движок: полнотекст, опечатки, релевантность, фильтры. Точечное чтение заказа по id остаётся в Postgres.
- Индекс, документ, анализатор — на уровне «что происходит с текстом запроса».
- Наполнение индекса: при сохранении товара сервис публикует событие из этапа 7, потребитель пишет документ в индекс.
- Поиск товаров: текст, фильтр по цене, пагинация.
- Рассинхрон: товар уже в Postgres, в поиске появится чуть позже. Это нормальное свойство такой схемы, его нужно уметь назвать.

Итог: поиск идёт в Elasticsearch, карточка товара и заказ читаются из Postgres, индекс догоняет базу через сообщение.

Глубокая настройка кластера, шардирование и своих анализаторов под язык — отдельный контур, сюда не входит.

## 9. Архитектура большого проекта

Около 2 недель. Собрать предыдущие этапы в форму, в которой живёт долгий сервис.

- Фича-модули: `catalog`, `orders`, `search`, `notifications`.
- Общий модуль только для конфигурации, логирования и базы. Свалка `utils` не заводится.
- Границы: контроллер тонкий, сценарий в сервисе, SQL в репозитории, поиск за своим клиентом Elasticsearch, брокер за своим publisher и consumer.
- Циклическая зависимость между модулями: поймать на учебном примере и разрезать границей.
- Наблюдаемость: лог с идентификатором запроса, health check на Postgres, Redis и брокер.
- Короткий обзор адаптера Fastify и микросервисного транспорта Nest. Выделять сервисы в отдельные процессы только если сможете объяснить, какая граница модулей уже не выдерживает один процесс.

Итог: новая фича добавляется модулем. Каталог, заказы, кэш, событие и поиск связаны явно, а не через общие импорты «отовсюду».
